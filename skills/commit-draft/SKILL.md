# Draft a commit message

Produces one Conventional Commits message from the change currently in the working tree.
Never commits, stages, pushes, or edits code. Output the message only.

## Delegation

Reading a full diff is token-heavy and mechanical, so this is worth pushing into a subagent
and keeping out of the main context.

If your runtime supports subagents, spawn one with the body of `../../agents/commit-drafter.md`
as its instructions (ignore that file's YAML frontmatter — it is packaging metadata, the
prose below it is the prompt). Give it shell access and file reads; tier `cheap` is
sufficient. Present its output verbatim; do not re-summarise the diff yourself.

If your runtime has no subagents, follow the procedure below inline. It is the same
instructions, expanded.

## Procedure

### Step 1 — read the change

Run these three commands and read all of their output:

```bash
git status --short
git diff --staged
git log --oneline -15
```

If `git diff --staged` prints nothing, nothing is staged. Run `git diff` instead and say in
one line that you are describing unstaged changes.

`git log --oneline -15` exists so you can match the repo's existing subject style. If the
repo already uses Conventional Commits, match it. If it plainly does not, match what it
does use instead — consistency with the repo beats consistency with this document.

### Step 2 — pick the type

Read the diff and choose exactly one type from this table. If two apply, pick the one
highest in the table.

| Type | Use when the diff |
| --- | --- |
| `feat` | adds a capability a user can invoke |
| `fix` | corrects behaviour that was wrong |
| `perf` | makes existing behaviour faster or lighter, same result |
| `refactor` | restructures code with no behaviour change |
| `docs` | changes only documentation or comments |
| `test` | changes only tests or fixtures |
| `build` | changes build config, packaging, or dependencies |
| `ci` | changes CI workflow files only |
| `chore` | anything else — version bumps, file moves, config |

### Step 3 — pick the scope

The scope is one lowercase noun naming the area touched: a module, package, directory, or
subsystem name taken from the actual paths in the diff. Examples: `auth`, `parser`, `api`,
`cli`. If the diff spans more than two unrelated areas, omit the scope entirely rather than
inventing an umbrella term.

### Step 4 — write the subject line

Format: `type(scope): subject`

Rules, all mandatory:

- Imperative mood — "add", not "added" or "adds".
- No capital letter at the start of the subject.
- No trailing full stop.
- The whole line is 72 characters or fewer.
- Describe the **effect** of the change, not the files touched. "preserve hand-written tags
  when pruning" beats "update TagSynchronizer.cs".

### Step 5 — decide whether a body is needed

Write a body **only** if at least one of these is true. Otherwise stop after the subject
line — a one-line message is the correct answer for a small obvious change.

- The change fixes a bug, and the symptom is not obvious from the diff.
- There is a non-obvious tradeoff or a rejected alternative worth recording.
- Users will notice a behaviour change.
- Data or a generated file was regenerated, and the source matters.
- A dependency, minimum runtime version, or ABI target was bumped.

If you write a body: leave one blank line after the subject, wrap at 72 columns, and explain
**why**, not what. The diff already says what. Bullets with `-` are fine.

### Step 6 — mark breaking changes

If the change breaks a public API, a CLI flag, a config key, or an on-disk format, do both:

1. Put `!` before the colon: `feat(api)!: drop v1 endpoints`
2. Add a footer paragraph starting exactly `BREAKING CHANGE: ` describing what breaks and
   what the user must do.

### Step 7 — self-check before returning

- [ ] Subject line is 72 characters or fewer.
- [ ] Type is one of the nine in the table.
- [ ] Subject is imperative, lowercase, no trailing period.
- [ ] Every claim in the message traces to something actually in the diff.
- [ ] No credit to yourself, no "generated by", no padding.
- [ ] Breaking changes carry both `!` and a `BREAKING CHANGE:` footer.

## Output

Output the commit message and nothing else. No preamble, no explanation, no code fences
around it. The user will copy it directly.

## Worked example

Diff: a null check added to `src/auth/session.py`, plus a regression test.

```text
fix(auth): reject sessions with a missing user id

A session cookie carrying a null user id passed validation and was treated
as an authenticated anonymous user, granting read access to any endpoint
that only checked "is a session present".

The check now requires a non-null id. Existing valid sessions are
unaffected; malformed ones now fail closed at validation time.
```

## PR descriptions

If the user asked for a PR description rather than a commit message, read the diff the same
way but output this structure instead:

```markdown
## What

One paragraph, plain language, on what changes for a user of this project.

## Why

The problem this solves. Link the issue if the branch name or commits reference one.

## How

Only the non-obvious implementation decisions. Skip this section if there are none.

## Testing

What you ran, and what a reviewer should run to confirm it.
```
